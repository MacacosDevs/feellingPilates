per-source switch, synthetic real route, historical mode or autonomous retry.
Request: run UUID, fresh attempt UUID, exact LocalDate, explicit IANA business ZoneId,
nonempty set of salon UUIDs for R1/R2 scope, fixed R6 catalog `F2E-R6-COORDINATION-V1`,

Reject null/blank/NUL/malformed UTF-8, duplicates before set conversion, unapproved

before opening SQL. Never derive date/zone from server clock/default timezone.

The frozen implementation handoff must bind concrete hard maximum rows/bytes/SQL/
elapsed time and timeout from measured acceptance fixtures. Unbounded operation is
forbidden; no productive performance claim is made by this documentary design.
Exceeding any limit aborts, never truncates or silently pages a partial universe.
Global R3/R4 exact-date reads remain global even when R1/R2 salon scope is smaller.
No ranges: a date list is external scheduling of separate units with separate results,
not a shared snapshot across dates. R6 never installs that scheduling trigger here.

Use typed length-prefixed canonical UTF-8 fields with explicit null/presence and list
counts (no delimiter concatenation), SHA256 domain-separated by version. UUID sort
is unsigned 16-byte order, text sort unsigned UTF-8, V2 references use type/unsigned UUID/date order. Preserve every closed source formula
and its own core/reference ordering verbatim; the old reference comparator is signed.
Request commitment binds every request field including budgets; invocation identity
binds request commitment + owner-reserved nonce; boundary identity binds invocation
+ native resource generation. Source execution identities remain original participant
commitments. Shared snapshot identity binds boundary + initial observed pg snapshot +
actual descriptor commitments, not time or a caller string. R6 ledger identity binds
invocation + comparison rule/version + source type + original source identity + fixed
group/axis. Retain V2 evaluation identity formula unchanged: invocation, V2 rule, source
type/identity and scenario; its axis is determined by group and bound in full evidence.

may share content with different comparison-only metadata; original participant/R5

attempts are not promised equal content commitments.

No self/future-hash cycles: planned catalog/bind commitments exist before execution;
observed statement events bind them after execution; participant execution evidence
binds those events; completion receipt binds participants/global capture and outcome;
completed envelope binds receipt; composition binds envelope; final result binds all
outputs. Do not hash a receipt into a field on which that receipt itself depends.

## 4. Sole physical owner, capability and completion

The isolated outer facade calls a DIFFERENT public Spring-proxied acquisition owner
method. Owner uses exact registered `f2eReaderTransactionManager`, REQUIRES_NEW,
REPEATABLE_READ, readOnly=true and bounded timeout. Reject an already active ambient
transaction at the facade; REQUIRES_NEW is the defensive owner boundary, not permission
to suspend productive work. No nested participant owner, async/parallel read, retry,
self/new invocation, default-manager fallback or transaction suspension in the unit.
All physical participants use MANDATORY on that same actual manager; R5 owns none.

Before material queries, observe and bind actual registered manager, DataSource,
EMF, transaction-bound shared EntityManager/holder, Hibernate Session, JDBC connection
and native PgConnection object identity/generation. Endpoint/database/schema/principal
must match trusted descriptor. A proxy/unwrap label alone is insufficient. Validate
same thread, active transaction, physical isolation/read-only, backend session and
resource generation at admission and every stage; capture rejects any other connection.
No participant may acquire its own connection or alter transaction settings.

Owner privately reserves one invocation and one exact context instance per expected
participant; registry key includes invocation/thread/owner/manager/boundary/resource/
capture/catalog/scope. Admission is one-use RESERVED→ADMITTED→CONSUMED, in scheduled
order only. Caller supplies no physical/schema/source/capture SUCCESS fields. Copied
equal context, foreign attempt, changed scope/binds, stale generation, reused reservation,
nested capture, reentrancy, wrong proxy or unknown participant invalidates the unit.
Contexts and reservations are never public authority-bearing constructors. Immutable
metadata values may be public but cannot mint the private capability.

Capture opens before first observed SQL and stays live through transaction completion
and resource cleanup; catalog policy observes preparation, named and positional typed
binds, execution success/failure and row shape/count on the same connection. Owner
initial/final probes observe isolation/read-only, resource/principal and
`pg_current_snapshot()::text`; compare exact normalized observations. Snapshot equality
is necessary, never sufficient without the owner/resource/capture/completion proof.
PostgreSQL RR fixes visibility at the first non-control statement; no serializability
or enforcement of productive business invariants is claimed.

Private state progression: VALIDATED→RESERVED→TX_ACTIVE→INITIAL_VERIFIED→READS_VALIDATED
→FINAL_VERIFIED→BODY_RETURNED_PROVISIONAL→COMPLETED→RELEASED. Failure from any state is
terminal ABORTED. BODY_RETURNED is not success. A trusted synchronization observes
committed completion and captures failures; the OUTER facade waits for normal return
through the transaction interceptor, confirms committed status, no rollback-only,
no completion/cleanup exception and sealed capture with no extra SQL. UNKNOWN,
rollback, commit failure, after-completion failure or incomplete capture all abort.
No database probe after commit can prove the old snapshot; completion uses retained
in-transaction observations plus actual transaction-manager outcome.

Only then issue immutable completion receipt with invocation/boundary/resource,
initial/final observations, descriptors, planned and observed capture commitments,
participant identities/counts, positive completion and authority versions. Remove
all registry/ThreadLocal state in finally on success and failure; destroy capabilities.
No reusable token survives pool connection return. No managed entity/proxy/collection,
stream, EM, Session, Connection or transaction handle escapes. R5 and comparisons run
outside TX over copied scalar DTOs. Any later pure failure discards the whole final
result too; completion alone does not authorize partial diagnostic release.

## 5. Fixed orchestration, manifest and schema trust

Execution order is fixed, sequential, no per-reader retry:

1. Validate request and accepted A/B authority; freeze catalog/limits and actual objects.
2. Start owner/capture; run initial RR/read-only/resource/principal/snapshot and descriptor
   probes; validate actual V47/50 Flyway history/checksums and required schema slices.
3. R1 once: readByScope with exact requested salons and desde=hasta=request date.
4. R2 once: readForDate with the same salons/date, preserving its member/assignment order.
5. R3 once: global nominal for date; keep every applicable series/date and full backing.
6. R4 once: global active adjustments for date; keep all physical adjustment backing.
7. Derive conservative validity coverage; execute §6's scalar reads in its fixed order.
8. Validate source/coverage/capture/binds/descriptor; run final probes in the same initial
   order. Every participant's own final checks remain mandatory; no coalescing probes.
9. Complete physical transaction as §4. Authenticate envelope, compose R5 exactly once,
   validate R5 output/backing and then execute §7 comparisons; release once atomically.

The global manifest is ordered concatenation OWNER_INITIAL + R1_SCOPE + R2_CLOSED +
R3_CLOSED + R4_CLOSED + VALIDITY_ORDER + OWNER_FINAL; completion events are a separate
ordered non-SQL suffix. Each segment includes all its required metadata/schema/data
probes, not merely its material query. R3's current nine-entry expectedManifest and
R4's current seventeen-entry manifest remain exact historical obligations; A/B must
version any future integration-specific observation differences explicitly. R2 has
its own sealed multi-statement manifest; R1 scope query/binds remain closed. R6 does
not replace participant captures with its global capture: private subsegments bind
one-to-one to the complete global event sequence and their participant identities.

Every statement has versioned logical ID, exact normalized SQL byte digest, permitted
phase, multiplicity/order, named Java/JDBC types, all positional occurrences, expected
bind values/collection order, projection scalar metadata and failure outcome. Repeated
parameters count at every position. No extra/omitted/reordered SQL, fetch/lazy SELECT,
uncatalogued metadata/JDBC work, driver retry, write CTE, multi-statement SQL, locks,
sequences, functions with side effects or setting changes is admitted. Trusted
transaction-control BEGIN/configure/COMMIT/ROLLBACK is separately captured/validated,
not smuggled into the SELECT material catalog. Catalog identities do not prove bind
or execution success. An inspector's seen-SQL list alone is insufficient.

The exact SQL bytes/hashes, descriptor SQL and bind-position inventory for new R6
support are frozen and independently audited in its future implementation handoff;
this design fixes relational scope below, not fabricated executable catalog evidence.
A/B must close any old-context predeclared-capture versus observed-capture formula
compatibility without circular identity or weakened observations. Missing prerequisite
or exact manifest is an admission failure before an implementation run, not discretion
for the implementer to improvise one.

Actual descriptor includes endpoint/database/schema/principal, PostgreSQL/JDBC/provider
versions, table/column/type/nullability/key/constraint/index definitions, relevant
privileges and actual ordered Flyway rows/checksums. Validate beginning and end on the
one resource; source-specific descriptor hashes need not equal one another. A shared
commitment binds all slices and source hashes. File migration count alone is not an
installed-schema proof. R3 V46/49 old acceptance and R4 V47/50 acceptance stay intact;
new V47 compatibility must prove all required R3/R4/validity slices. No new migration,
assignment exclusion restoration or historical-link table is justified or authorized.
